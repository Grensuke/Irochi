## 4. DetectorOutput → Alert Mapping

### Mapping flow

```text
DetectorOutput (decision = detection)
        ↓
Alert candidate construction
        ↓
Dedup/update evaluation (§9, §11)
        ↓
├── No existing alert matches dedup identity → CREATE new Alert
├── Existing alert matches, new information  → UPDATE existing Alert
└── Existing alert matches, no new info      → DUPLICATE / no-op
        ↓
PostgreSQL INSERT (create) or UPDATE (update)
        ↓
AWAIT COMMIT
        ↓
success?
   ├── NO  → log/retry, do NOT publish
   └── YES → Redis Pub/Sub fan-out
```

No-op duplicates do not reach PostgreSQL or Redis Pub/Sub.

### Commit-before-notify ordering

BD-005 says: "An alert must be successfully committed to PostgreSQL before its ID/message is published to Redis Pub/Sub."

**LOCKED (BD-005):** The commit-before-notify ordering for new alert publication (INSERT) is inherited and locked.

**PROPOSED (this document):** BD-005's original wording references "PostgreSQL INSERT" because alert updates were not yet a distinct concept when BD-005 was written. This document proposes applying the same commit-before-notify invariant to UPDATE operations:

- **CREATE:** PostgreSQL INSERT → AWAIT COMMIT → Redis Pub/Sub **(LOCKED, BD-005)**
- **UPDATE:** PostgreSQL UPDATE → AWAIT COMMIT → Redis Pub/Sub **(PROPOSED)**

This extends BD-005's principle to a case its original wording didn't anticipate. The UPDATE extension is PROPOSED, not yet separately approved as LOCKED.

### `detected_at` field-name resolution

`Alert.detected_at` is a **direct passthrough** of `DetectorOutput.evaluated_at`.

| Alert field | Source | Meaning |
|---|---|---|
| `detected_at` | `DetectorOutput.evaluated_at` | Time the detector completed its evaluation |
| `created_at` | Generated by Alert Engine | Time the Alert record was constructed/first persisted |

The rename from `evaluated_at` to `detected_at` is for analyst-facing clarity — "detected at" is more meaningful in a security context than "evaluated at." The value is identical; no transformation is applied.

`detected_at` is **not** the raw event timestamp — that information is part of the provenance chain (§8) and the source FeatureRecords, not the alert timestamp.

### Which DetectorOutput decisions become Alerts

| DetectorOutput.decision | Alert action |
|---|---|
| `detection` | Alert candidate → dedup evaluation → CREATE or UPDATE or no-op |
| `no_threat` | Not an alert; no alert record created |
| `insufficient_data` | Operational telemetry; not a security alert |
| `invalid_input` | Operational error handling; not a security alert |
| `detector_error` | Operational error handling; not a security alert |

Only `detection` produces alert candidates. The other decision types are operational/diagnostic concerns, not security alerts, unless a future operational-event design explicitly decides otherwise.

### Status

**PROPOSED.**

## 5. Severity

### Ownership

- **DetectorOutput** provides `severity_candidate` — the detector's severity suggestion
- **Alert Engine** owns final `severity` assignment

The Alert Engine may accept the detector's suggestion or override it based on:
- Cross-signal context (e.g. multiple related detections)
- Analyst-defined severity policies
- Historical context for the entity

### Severity enum

```text
critical | high | medium | low | info
```

This matches the existing enum in BD-008, `alerts.py`, and `API_CONTRACT.md`.

### Structural representation

| Alert field | Source | Description |
|---|---|---|
| `severity` | Alert Engine | Final alert severity |
| `severity_candidate` | DetectorOutput | Detector's suggestion; preserved for audit/explainability |

Both are present on every alert. If the Alert Engine does not override, `severity = severity_candidate`.

### Status

**PROPOSED.** No numerical severity scores. No scoring formulas.

## 7. Evidence

### Structure

Alert evidence extends DetectorOutput evidence with Alert-Engine context:

```text
alert_evidence:
  detector_evidence:                ← preserved from DetectorOutput.evidence
    features_used:
      - feature_name: "packet_rate"
        value: 12400.5
        contribution: "high"
      ...
    features_missing:
      - feature_name: "source_ip_entropy"
        reason: "not_yet_available"
    summary: "string"
  alert_context:                    ← added by Alert Engine (proposed/placeholder)
    dedup_action: "created" | "updated"
    severity_override: bool
```

### Design principles

1. **DetectorOutput evidence is preserved, not replaced.** The alert carries the detector's full structured evidence under `detector_evidence`.
2. **Alert Engine adds context, not interpretation.** The `alert_context` indicates what the Alert Engine did (created vs updated, whether severity was overridden) without re-interpreting the detector's findings.
3. **`evidence_summary`** is a separate top-level string field (§3) derived by the Alert Engine for analyst display. It is a presentation concern, not part of the structured evidence.
4. **Alert-context fields are proposed/placeholder.** Exact fields and typing will be refined during implementation. Do not treat `alert_context` sub-fields as finalized.

### What is preserved vs transformed

| Aspect | Handling |
|---|---|
| `features_used` | Preserved unchanged from DetectorOutput |
| `features_missing` | Preserved unchanged from DetectorOutput |
| `summary` (detector) | Preserved under `detector_evidence.summary` |
| `evidence_summary` (alert) | Derived by Alert Engine for analyst-facing display |
| `dedup_action` | Added by Alert Engine (proposed) |
| `severity_override` | Added by Alert Engine (proposed) |

### Status

**PROPOSED** (structural shape). **OPEN** (exact evidence field typing, exact alert_context sub-fields).

## 8. Provenance

### Provenance chain

```text
Raw event (Zeek/NetFlow/IPFIX)
        ↓  (ingest_timestamp, sensor_source)
CanonicalEvent
        ↓  (event_id, connection_id)
FeatureRecord
        ↓  (feature_id, revision, provenance)
DetectorInput
        ↓  (input_id, feature_id)
DetectorOutput
        ↓  (output_id, input_id, source_feature_references)
Alert
        ↓  (alert_id, detector_output_id, source_feature_references)
```

### Alert-level provenance fields

| Field | Type | Description |
|---|---|---|
| `detector_output_id` | UUID/string | Reference to the current/latest DetectorOutput represented by this alert; set on creation and updated when a valid newer DetectorOutput updates the alert. |
| `source_feature_references` | list of `{feature_id, revision}` | Identifies the exact FeatureRecords that contributed; passthrough from DetectorOutput |
| `detector_version` | string | Version of the detector logic |
| `model_version` | string | ML model version (if applicable) |

### Design principles

1. **References over copies.** Alert does not duplicate raw events, FeatureRecords, or DetectorOutputs. It stores references (`detector_output_id`, `source_feature_references`) that allow tracing.
2. **Upstream provenance shape remains OPEN.** The exact structure of FeatureRecord's `provenance` field (which references raw events) is OPEN upstream (Feature/Window v7 §5). Alert Schema inherits `source_feature_references` without depending on the raw-event provenance shape.
3. **Sufficient for investigation.** An analyst can trace: Alert → DetectorOutput → FeatureRecords → (via provenance) raw events.

### Status

**PROPOSED.**

## 9. Alert Identity / Deduplication

### Two distinct identities

| Concept | Field | Purpose | Mutability |
|---|---|---|---|
| **Alert identity** | `alert_id` | Unique record identity; identifies one persisted alert row | Immutable after creation |
| **Deduplication identity** | `dedup_identity` | Identifies when repeated DetectorOutputs refer to the same logical alert | Computed per incoming DetectorOutput |

`alert_id` is **not** the deduplication key. An alert's `alert_id` is assigned once at creation; subsequent DetectorOutputs for the same logical alert match on `dedup_identity` and update the existing `alert_id` rather than creating a new one.

### Structural deduplication key

```text
dedup_identity = (detector_id, threat_type, entity_type, entity_key)
```

This key determines: "is this DetectorOutput about the same threat affecting the same entity as an existing alert?"

### Deduplication evaluation

When a new DetectorOutput (with `decision = detection`) arrives:

1. Compute `dedup_identity` from the DetectorOutput
2. Search for an existing alert with matching `dedup_identity` that is in an active lifecycle state
3. Result:
   - **No match** → CREATE new alert
   - **Match found, new information** → UPDATE existing alert (§11)
   - **Match found, no new information** → no-op

### Temporal scoping

Whether the dedup identity includes a temporal dimension (e.g. "same threat within 1 hour = same alert" vs "same threat until resolved") remains **OPEN**. The structural key is defined; the temporal policy is an implementation decision.

### Naming distinction from upstream

The detector's **base grouping identity** = `(detector_id, entity_key)` (Detector I/O §11) identifies which entity a detector evaluates. The alert's **deduplication identity** = `(detector_id, threat_type, entity_type, entity_key)` identifies which DetectorOutputs refer to the same logical alert. These are distinct concepts:

- Base grouping identity operates at the feature/detector layer
- Deduplication identity operates at the alert layer and includes `threat_type` (because `tls_c2_detector` may emit separate alerts for `c2_beaconing` and `encrypted_malware` for the same entity)

### Status

**PROPOSED** (structural dedup key). **OPEN** (temporal scoping, exact dedup algorithm implementation).

## 10. Alert Lifecycle

### Status enum

```text
new | investigating | closed | false_positive
```

This reuses the existing enum from `backend/app/schemas/alerts.py` and `API_CONTRACT.md`. The existing enum adequately represents the required analyst workflow:

| Status | Meaning | Set by |
|---|---|---|
| `new` | Alert created, not yet reviewed by an analyst | Alert Engine (on creation) |
| `investigating` | Analyst has begun review | Analyst action |
| `closed` | Analyst has completed investigation | Analyst action |
| `false_positive` | Analyst has determined the alert is not a real threat | Analyst action |

### Semantic notes

- **`closed` is an analyst workflow status.** It does NOT imply that Irochi mitigated or stopped the threat. Irochi is a passive detection system (Architecture §1, AGENTS.md).
- **`false_positive` is an analyst judgment**, not an automatic detector decision. A detector returning `no_threat` does not set `false_positive` — it simply does not produce an alert.
- **`new` is the only status set by the Alert Engine.** All other transitions are analyst-initiated.

### Detector decision vs Alert lifecycle

These are structurally separate concerns:

| Concept | Values | Owner |
|---|---|---|
| DetectorOutput.decision | `no_threat`, `detection`, `insufficient_data`, `invalid_input`, `detector_error` | Detector |
| Alert.status | `new`, `investigating`, `closed`, `false_positive` | Alert Engine (initial) / Analyst (transitions) |

A detector finding a threat (`decision = detection`) creates a `new` alert. It does not set the alert to `investigating`, `closed`, or any other analyst workflow state.

### Why not a new enum

The existing `new / investigating / closed / false_positive` enum was evaluated against alternatives such as `open / acknowledged / resolved / dismissed`. The existing enum:

- Already distinguishes un-reviewed (`new`) from under-review (`investigating`)
- Distinguishes completed-investigation (`closed`) from false-alarm (`false_positive`)
- Is already implemented in the dummy backend and API contract
- Avoids migration/compatibility cost

No concrete semantic gap was identified that would justify the rename. Under deadline pressure, the existing enum is preferred.

### Status

**PROPOSED.**

## 11. Alert Update / Amendment

### When updates occur

A later DetectorOutput may update an existing alert when:
- The dedup identity (§9) matches an existing active alert
- The new DetectorOutput provides new information (higher confidence, new evidence, updated severity candidate)

### Update behavior

| Aspect | Handling |
|---|---|
| `detected_at` | Unchanged (preserves original detection time) |
| `last_seen_at` | Updated to the new DetectorOutput's `evaluated_at` |
| `confidence` | Updated if new value is higher; exact policy OPEN |
| `severity_candidate` | Updated to reflect latest detector suggestion |
| `severity` | Alert Engine re-evaluates; may change |
| `evidence` | Merged/updated — exact merge strategy OPEN |
| `source_feature_references` | Extended with references from the new DetectorOutput |
| `detector_output_id` | Updated to the most recent triggering DetectorOutput |
| `update_count` | Incremented |
| `status` | NOT changed by detector updates — analyst workflow is separate |

### Staleness protection

A DetectorOutput should not overwrite an alert with stale information. Staleness is determined by:

- `evaluated_at` comparison: a DetectorOutput with an earlier `evaluated_at` than the alert's `last_seen_at` is potentially stale
- Source feature revision comparison (per-feature, per Detector I/O §13)

The exact staleness-rejection algorithm remains **OPEN**.

### Late amendments

If a DetectorOutput arrives after the alert has been `closed` or `false_positive`:

- The alert is **not** automatically reopened
- The late DetectorOutput is logged for audit but does not modify the alert state
- Whether to create a new alert for the same dedup identity with a new temporal scope is an implementation decision (OPEN)

### Status

**PROPOSED** (structural update model). **OPEN** (exact merge strategy, staleness algorithm, late-amendment policy).

## 12. Multiple Threat Types

### MVP preference: one Alert per threat_type

When a single detector evaluation identifies multiple threat types (producing multiple DetectorOutputs per Detector I/O §15), each threat type becomes a **separate Alert**.

Example: `tls_c2_detector` evaluates a pair entity and finds evidence for both `c2_beaconing` and `encrypted_malware`. Per Detector I/O §15, it emits two separate DetectorOutputs, one per threat type. Each DetectorOutput produces a separate alert candidate with its own `dedup_identity`.

### Distinction from repeated-detection dedup

This MVP preference is **independent** of the deduplication/update behavior defined in §9/§11:

- **Different threat types from one evaluation** → separate Alerts (this section)
- **Repeated DetectorOutputs for the same threat_type and entity over time** → create-or-update dedup logic in §9/§11; they do NOT each produce a new Alert

These are orthogonal decisions. The MVP one-Alert-per-threat_type preference concerns whether simultaneously-emitted different threats share an Alert. The dedup logic concerns whether sequentially-emitted identical threats create new Alerts.

### Status

**PROPOSED** (MVP one-Alert-per-threat_type).

## 13. Multi-Detector Correlation

### MVP baseline

In MVP, each detector's alert lineage remains independent and is subject to the deduplication/update behavior defined in §9/§11. There is no dedicated cross-detector correlation entity.

Example: if `ddos_detector` and `recon_detector` both detect activity from the same `src_ip`, they produce independent alerts with different `detector_id` and `threat_type` values, and therefore different `dedup_identity` values.

### Future capability (OPEN)

Cross-detector incident grouping — correlating related alerts from different detectors into a higher-level "incident" — is explicitly **OPEN**. This could be supported through:

- An `incident_id` field on alerts (grouping mechanism)
- A separate incident/case management entity
- Post-hoc analytical correlation

Alert Schema does not preclude future incident grouping, but does not implement it.

### Status

**OPEN.**

## 14. Entity and Timestamp Model

### Entity types

Alert inherits entity types from DetectorOutput:

| entity_type | entity_key format | Example |
|---|---|---|
| `source` | IP address | `10.0.2.15` |
| `destination` | IP address | `10.0.5.20` |
| `pair` | `src_ip\|dst_ip` | `10.0.2.15\|203.0.113.47` |
| `connection` | connection identifier | `conn_id_xyz` |
| `event` | event identifier | `event_id_abc` |

### Timestamp semantics

| Timestamp | Type | Set when | Meaning |
|---|---|---|---|
| `detected_at` | int64 | Alert creation | Time the detector completed evaluation; passthrough of DetectorOutput.evaluated_at |
| `created_at` | int64 | Alert creation | Time the Alert record was constructed/first persisted |
| `first_seen_at` | int64 | Alert creation; unchanged on updates | Earliest accepted detection time within this alert instance's resolved dedup scope |
| `last_seen_at` | int64 | Alert creation; updated on subsequent detections | Most recent accepted detection time within this alert instance's resolved dedup scope |
| `resolved_at` | int64 | Status transition to `closed` or `false_positive` | Time the analyst resolved/dismissed the alert |

### Timestamps not included

- **Raw event timestamp** is not a direct alert field. It is accessible through the provenance chain (§8): Alert → source_feature_references → FeatureRecord → raw event.
- **`updated_at`** (generic modification timestamp) is not a separate field — `last_seen_at` serves the detection-update role, and `resolved_at` serves the analyst-action role. A generic `updated_at` could be added at the PostgreSQL layer if needed.

**PROPOSED.**

## 15. Alert Title / Summary

### Title

`title` is a short, deterministic, analyst-facing label derived from:

- `threat_type` → human-readable threat name
- `entity_key` → the affected entity
- `detector_id` → (optional) the detecting module

Example derivation pattern (exact templates are an implementation detail):

```text
"{ThreatName} — {entity_key}"
"Volumetric DDoS — 10.0.5.20"
"C2 Beaconing — 10.0.2.15|203.0.113.47"
```

### Evidence summary

`evidence_summary` is a human-readable string derived by the Alert Engine from the structured evidence. It is a presentation field — the canonical evidence is the structured `evidence` object (§7).

### Design principles

- **Deterministic derivation.** Title and summary are derived from detector/threat metadata, not hand-written per alert.
- **Implementation details left open.** Exact template strings, localization, and formatting are not defined here.
- **No hard-coded dozens of message templates** in this document.

### Status

**PROPOSED.**

## 16. API Presentation Boundary

### Canonical Alert Schema vs AlertResponse

The Alert Schema (this document) defines the **canonical, persistence-ready alert object**. The `AlertResponse` in `backend/app/schemas/alerts.py` is the **API presentation model** — what the REST/WebSocket layer exposes to the frontend.

Building on the comparison already established in DETECTOR_IO_CONTRACT_DRAFT_v1.md §18:

| Aspect | Canonical Alert (this doc) | Current AlertResponse (dummy API) | Reconciliation |
|---|---|---|---|
| Evidence | Structured `evidence` object | `evidence_summary` (string only) | AlertResponse will expose `evidence_summary` derived from the canonical structured evidence. Whether to also expose the full structured evidence is an API design decision. |
| Lifecycle | `status` (same enum) | `status` (same enum) | Compatible — same values |
| Provenance | `source_feature_references`, `detector_output_id`, `detector_version`, `model_version` | Not present | AlertResponse may expose a subset for investigation UI. Final API Contract decision. |
| Dedup | `dedup_identity`, `update_count` | Not present | Internal fields; may not be exposed in API. |

## 18. Redis Pub/Sub Boundary

### Preserved ordering

```text
Alert Engine
        ↓
PostgreSQL INSERT or UPDATE
        ↓
AWAIT COMMIT
        ↓
success?
   ├── NO  → log/retry, do NOT publish
   └── YES → Redis Pub/Sub
```

This applies to **both** new alerts (INSERT) and updates to existing alerts (UPDATE). The update path is not exempt from commit-before-notify ordering — see §4 for the full rationale.

### What is published

The alert published to Redis Pub/Sub represents the **successfully persisted canonical alert state**, whether that state was reached via a new row or an update to an existing row.

No-op duplicates (§4, §9) are not published to Redis Pub/Sub.

### What this document does NOT design

- Redis Pub/Sub channel/topic names
- Message format (the canonical alert object is the content; the transport envelope is a Redis/WebSocket concern)
- Redis Pub/Sub retention or reliability
- Fan-out to multiple WebSocket workers

These belong to the infrastructure/implementation layer.

### Status

**PROPOSED** (ordering preserved). **OPEN** (Redis Pub/Sub transport details).

## 19. Error / Invalid Alert Handling

### Structural behavior

| Condition | Handling | Result |
|---|---|---|
| **Valid DetectorOutput, decision = detection** | Alert candidate → dedup evaluation → create/update/no-op | Normal flow (§4) |
| **Valid DetectorOutput, decision ≠ detection** | Not an alert candidate | Operational telemetry (§4) |
| **Invalid DetectorOutput** (schema mismatch, missing required fields) | Reject; log error | No alert created; operational error |
| **Unknown detector_id** | Reject; log error | No alert created |
| **Unknown threat_type** | Reject; log error | No alert created |
| **Missing required alert field** (after mapping) | Reject; log error | No alert created; indicates mapping/validation bug |
| **Stale DetectorOutput** (evaluated_at < alert's last_seen_at) | Discard; log for audit | Existing alert not modified |
| **Duplicate DetectorOutput** (same dedup identity, no new info) | No-op; may log | Existing alert not modified; no Pub/Sub publish |

### Design principles

- **Reject invalid input; do not fabricate alerts.** An alert with unknown detector_id or threat_type is not a valid security alert.
- **Log operational errors for observability.** Invalid/rejected alert candidates should be visible in structured logging and Prometheus metrics.
- **Do not design HTTP/API error responses here.** API-level error handling is a Final API Contract concern.

### Status

**PROPOSED.**

### Alert update revision

`update_count` serves as a lightweight revision counter:
- 0 on creation
- Incremented on each update via §11

This is sufficient for detecting concurrent-modification conflicts at the application level. Whether a more formal revision/versioning mechanism is needed depends on the PostgreSQL Schema design (e.g. optimistic locking).
