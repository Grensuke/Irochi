# SIH26145 — CANONICAL EVENT SCHEMA

> **Status:** Logical schema baseline for implementation planning.
>
> **Purpose:** Defines the source-independent event contract produced by the Python Ingest Normalizer before events enter Redpanda.
>
> **Design rule:** This document defines **observed/normalized facts**. Derived/windowed features belong to the Feature/Window Schema and are intentionally excluded here.
>
> **Implementation note:** The logical schema should be reviewed against the actual Zeek configuration, JA3/JA4 package output, and the chosen NetFlow/IPFIX exporter before final Pydantic implementation.

---

# 1. Schema Shape

The canonical event is **not one flat record**.

```text
CanonicalEvent
├── Envelope
└── Typed Payload
    ├── ConnectionPayload
    ├── DnsPayload
    └── TlsPayload
```

The `event_type` field determines the payload type.

```text
event_type = connection → ConnectionPayload
event_type = dns        → DnsPayload
event_type = tls        → TlsPayload
```

A `connection` event represents normalized flow/connection telemetry and is the common flow-level representation for Zeek `conn.log`, NetFlow, IPFIX, and potentially sFlow inputs.

DNS and TLS events are Zeek-derived because NetFlow/IPFIX/sFlow do not provide the required application-layer DNS/TLS information.

# 3. Canonical Event Envelope

Every canonical event carries the envelope.

| Field | Type | Required | Description |
|---|---|---:|---|
| `event_id` | UUID/string | Yes | Unique identifier generated by the Normalizer |
| `event_type` | enum string | Yes | `connection`, `dns`, or `tls` |
| `connection_id` | string | Yes | Stable flow/connection correlation identifier |
| `timestamp` | int64 | Yes | Canonical event time as epoch microseconds |
| `timestamp_precision` | enum/string | Yes | Actual precision of the source timestamp |
| `ingest_timestamp` | int64 | Yes | Time the Normalizer emitted the event, epoch microseconds; generated locally by the Normalizer and therefore always available when a canonical event is emitted |
| `sensor_source` | enum string | Yes | `zeek`, `netflow`, `ipfix`, or `sflow` |
| `src_ip` | IP address string | Yes | Normalized source IP |
| `dst_ip` | IP address string | Yes | Normalized destination IP |
| `src_port` | integer | Optional | Source port; null for protocols without an applicable transport port |
| `dst_port` | integer | Optional | Destination port; null for protocols without an applicable transport port |
| `protocol` | enum/string | Yes | Normalized protocol, e.g. `tcp`, `udp`, `icmp`, `other` |
| `protocol_number` | integer | Optional | Raw IANA protocol number where available |
| `schema_version` | string | Yes | Version of the canonical event contract |

## Timestamp decision

Internal canonical representation:

```text
timestamp = int64 epoch microseconds
```

The API layer may serialize the timestamp as RFC 3339 later.

`timestamp_precision` preserves the actual precision of the source so second-granularity NetFlow/IPFIX data is not falsely represented as microsecond-accurate observations.

## `ingest_timestamp` decision

`ingest_timestamp` is **required**.

Because it is generated by the Normalizer at the moment the canonical event is emitted, it does not depend on source timestamp availability or precision. It is primarily used for:

- pipeline-lag measurement,
- latency/observability analysis,
- debugging ordering and ingestion behaviour.

It is not a threat-detection feature.

# 4. `connection` Payload

## Sources

```text
Zeek conn.log
NetFlow
IPFIX
sFlow (if implemented)
```

## Fields

| Field | Type | Required | Source availability | Purpose |
|---|---|---:|---|---|
| `duration` | float | Optional | Zeek; derivable from flow start/end when available | Connection duration |
| `orig_bytes` | integer | Optional | Zeek; NetFlow/IPFIX only when reliable biflow direction exists | Bytes sent by originator |
| `resp_bytes` | integer | Optional | Zeek; NetFlow/IPFIX only when reliable biflow direction exists | Bytes sent by responder |
| `orig_pkts` | integer | Optional | Zeek; NetFlow/IPFIX only when reliable biflow direction exists | Packets sent by originator |
| `resp_pkts` | integer | Optional | Zeek; NetFlow/IPFIX only when reliable biflow direction exists | Packets sent by responder |
| `conn_state` | string | Optional | Zeek only | Zeek connection-state code |
| `history` | string | Optional | Zeek only | Zeek connection flag/history string |
| `tcp_flags` | integer/bitmask | Optional | NetFlow/IPFIX where exported | Source-native cumulative TCP flags |
| `service` | string | Optional | Zeek only | Zeek best-effort application-protocol identification |
| `local_orig` | boolean | Optional | Zeek only | Whether originator is local to monitored network |
| `local_resp` | boolean | Optional | Zeek only | Whether responder is local to monitored network |

## Directional field rule

The canonical schema uses Zeek-aligned directional names:

```text
orig_bytes
resp_bytes
orig_pkts
resp_pkts
```

Do **not** automatically map NetFlow/IPFIX fields such as `IN_PKTS` and `OUT_PKTS` to `orig_*` and `resp_*`.

A NetFlow/IPFIX exporter must first positively establish originator/responder direction semantics through an appropriate direction indicator (such as `flowDirection`) or documented exporter semantics.

If reliable originator/responder alignment cannot be established:

```text
orig_bytes = null
resp_bytes = null
orig_pkts  = null
resp_pkts  = null
```

and the raw source fields may be retained for provenance/debugging.

This rule blocks implementation of that mapping until the actual exporter is known and its semantics are verified.

# 5. `dns` Payload

## Source

```text
Zeek dns.log
```

NetFlow/IPFIX/sFlow do not supply the DNS application-layer data required by this payload.

## Fields

| Field | Type | Required | Description |
|---|---|---:|---|
| `query` | string | Yes | Queried DNS name |
| `qtype_name` | string | Yes | Human-readable query type such as A, AAAA, TXT, NS |
| `qtype` | integer | Optional | Numeric DNS query type |
| `rcode_name` | string | Optional | Human-readable response code |
| `rcode` | integer | Optional | Numeric response code |
| `answers` | list[string] | Optional | Answer record values |
| `rejected` | boolean | Optional | Whether the DNS query was rejected |
| `trans_id` | integer | Optional | DNS transaction identifier |
| `rtt` | float | Optional | DNS query round-trip time in seconds |

## DNS required/optional rule

A valid DNS canonical event may exist even when no matching response is observed.

Therefore:

```text
query       = required
qtype_name  = required

rcode       = optional
rcode_name  = optional
answers     = optional
rejected    = optional
rtt         = optional
```

# 6. `tls` Payload

## Sources

```text
Zeek ssl.log
explicitly installed/tested JA3 package
explicitly installed/tested JA4/JA4+ package
```

NetFlow/IPFIX/sFlow do not supply the application-layer TLS metadata required for this payload.

## Fields

| Field | Type | Required | Description |
|---|---|---:|---|
| `ja3` | string | Optional | JA3 client TLS fingerprint |
| `ja3s` | string | Optional | JA3S server TLS fingerprint |
| `ja4` | string | Optional | JA4 client TLS fingerprint |
| `ja4s` | string | Optional | JA4S server TLS fingerprint |
| `server_name` | string | Optional | TLS SNI/server name |
| `version` | string | Optional | Negotiated TLS version |
| `cipher` | string | Optional | Negotiated TLS cipher suite |
| `established` | boolean | Optional | Whether TLS establishment was observed |
| `validation_status` | string | Optional | Certificate validation status where available |
| `subject` | string | Optional | Certificate subject DN |
| `issuer` | string | Optional | Certificate issuer DN |

Fingerprint fields are optional because a valid TLS observation does not guarantee that every optional fingerprint package or fingerprinting stage produces a value.

# 7. JA3 / JA4 Design Rules

## JA3 MVP

The primary encrypted-session malware MVP signal is:

```text
raw ja3
   ↓
SSLBL intelligence lookup
   ↓
derived ja3_blacklist_match
```

`ja3_blacklist_match` is **not** part of the canonical event.

It belongs to Feature/Window processing.

## SSLBL caution

A blacklist match is supporting intelligence, not an automatic conviction.

Treat:

```text
ja3_blacklist_match
```

as a medium-confidence signal that should be combined with other evidence by the Alert Engine.

## JA4 / JA4S

JA4 and JA4S are retained as separate raw fields and are supplementary metadata in the MVP.

Do not assume a JA4 intelligence source has the same maturity as the JA3/SSLBL path.

## Multiple JA4+ logs

Do not collapse all JA4+ variants into:

```text
tls_fingerprint
```

Different JA4+ variants can originate from different Zeek logs.

Examples include:

```text
ssl.log
conn.log
http.log
x509.log
JA4 SSH-specific logs
```

Only fingerprint fields explicitly selected for the MVP should enter the relevant canonical payload.

Other variants remain outside the MVP unless another detector requires them.

# 8. `connection_id` Rules

`connection_id` is required in every canonical event.

## Zeek

Use the native Zeek connection UID.

## NetFlow/IPFIX

Preferred order:

```text
1. reliable exporter-provided flow ID
2. deterministic synthetic ID if no reliable native ID exists
```

The synthetic algorithm is still open because it depends on the actual exporter format and its flow-record semantics.

Do not use the previously considered simple time-bucket hash without reviewing the real exporter; it can merge distinct short-lived flows or split a real flow across bucket boundaries.

DNS/TLS events may use the underlying Zeek UID when correlation is available.

### sFlow caveat

sFlow is fundamentally **packet-sampled telemetry** rather than a full flow-accounting record in the same sense as NetFlow/IPFIX. Its values may be sampled/extrapolated, so connection identity, packet/byte counts, and directional semantics can be less precise.

For this reason:

- `sflow` remains in the canonical source taxonomy because it is named by the SIH problem statement.
- sFlow is **not an MVP implementation requirement**.
- Do not assume sFlow inherits the same `connection_id` or directional-mapping guarantees as a verified NetFlow/IPFIX exporter.
- Any future sFlow adapter must explicitly document its sampling and field semantics before mapping data into directional canonical fields.

# 9. Source Capability Matrix

| Detector capability | Zeek | NetFlow/IPFIX |
|---|---:|---:|
| DDoS | Yes | Yes |
| Recon | Yes | Yes |
| Exfiltration | Yes | Yes, when reliable directional/biflow information exists |
| DGA / DNS tunneling | Yes | No |
| TLS fingerprint-assisted malware | Yes | No |
| General C2 beaconing | Yes | Yes |

Important distinction:

```text
C2 beaconing
= flow timing, so it can run from connection events

TLS-fingerprint-assisted C2
= requires Zeek TLS metadata
```

# 10. Source Mapping Principles

The Normalizer is responsible for translating source-native names into the canonical vocabulary.

Examples:

```text
Zeek id.orig_h   → src_ip
Zeek id.resp_h   → dst_ip

Zeek id.orig_p   → src_port
Zeek id.resp_p   → dst_port

Zeek proto       → protocol

Zeek uid         → connection_id

Zeek ts          → timestamp
```

For NetFlow/IPFIX, the Normalizer maps only fields whose semantics are sufficiently understood.

It must not silently fabricate directional semantics.

# 12. UDP Amplification Boundary

The canonical schema stores raw observations only:

```text
orig_bytes
resp_bytes
orig_pkts
resp_pkts
protocol
src_port
dst_port
timestamp
```

The exact amplification/asymmetry feature remains conditional until the actual demo PCAP/sensor vantage point is reviewed.

Candidate derived measurements:

```text
amplification_ratio
unsolicited_response_rate
large_udp_response_rate
response/request byte asymmetry
reflector-source-port indicators
```

Do not hard-code one formulation into the Feature/Window Schema yet.
